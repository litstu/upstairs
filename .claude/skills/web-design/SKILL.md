# Web デザイン判断スキル

このスキルは「**どう書くか**（Tailwind / DaisyUI のクラスの使い方）」ではなく、「**何が良い見た目か**（方向性の判断基準）」を担当する。クラスの使い方は `.claude/.rules/coding-rules.md` の「デザインに関するガイド」を見ること。両方を併せて使う。

> 元ネタは Anthropic 公式の `frontend-design` スキル。原則はそのまま、実装ガイドだけ DaisyUI / ERB 用に置き換え、トーンを中高生キャンプ向けに調整している。

## このスキルを使う場面

1. **Design フェーズ（`/speckit-start` のフェーズ 3〜4）** — メンバーと「どんな雰囲気にするか」を会話したあと、このスキルに従って **方向性を 1 つに決め切り、`plan.md` の「デザイン仕様（固定）」に書き残す**。
2. **実装フェーズ（`/speckit-build` の dev-agent）** — `plan.md` に固定したデザイン仕様を読み、全画面で **同じ世界観を再現** する。ここで方向性を新しく決め直さない。
3. **見た目調整（`/speckit-feedback` の 🎨）** — 固定済みの方向性の中で微調整する。差し色や雰囲気を根本から変えるときは plan.md の仕様も更新する。

要するに「**判断は Design で 1 回、実装は再現に徹する**」。これがブレない見た目を作るコツ。

## 大原則：題材に根ざす

汎用的な見た目になる最大の原因は「**何のサービスか**」を見た目に反映していないこと。まず次を 1 つに決める。

- **題材**：何のサービスか（例：地元の銭湯を巡る記録サイト）
- **使う人**：誰のためか
- **このページの一番の仕事**：見た人に最初に何をしてほしいか

そのうえで、**題材の世界観**（色・モチーフ・言葉づかい）から具体的な選択を引き出す。銭湯なら暖簾の藍色とタイルの幾何学、レトロゲームならドット感、というように、題材そのものがデザインのヒントになる。メンバーのテーマを無視した「とりあえずキレイな UI」にしない。

## 避けるべき「AI が作った感」（AI slop）

指定がない限り、次の“いかにも”は使わない。これらは「選択」ではなく「逃げのデフォルト」。

- **DaisyUI のデフォルト `light` テーマのまま出荷する**（このプロジェクト最大の地雷）。`layout.erb` の `data-theme` を題材に合わせて必ず選び直す。
- クリーム色背景 ＋ 高コントラストの明朝 ＋ テラコッタの差し色、という“上品系”定番。
- ほぼ黒の背景 ＋ 蛍光グリーン / 朱色 1 色、という“ダーク系”定番。
- 細い罫線だらけの新聞風レイアウト。
- 意味のない `01 / 02 / 03` の連番装飾（**本当に順番があるとき以外は使わない**）。
- 中央寄せの一点張り、影の付けすぎ、虹色グラデ、絵文字（生成物では禁止。`coding-rules.md` 参照）。

題材で方向が決まっているなら、それに従うのが最優先。自由なところを“定番”で埋めない。

## 方向性をトークン化して固定する

Design フェーズで、次の 4 つを決めて `plan.md` の「デザイン仕様（固定）」に書く。これが実装の拠り所になる。

### 1. テーマ（DaisyUI の `data-theme`）

題材の雰囲気に合う DaisyUI テーマを 1 つ選ぶ。`light` のまま放置しない。目安：

| 題材・雰囲気 | DaisyUI テーマ候補 |
|---|---|
| かわいい・やさしい・パステル | `cupcake`, `pastel`, `valentine` |
| ポップ・元気・若者向け | `bumblebee`, `lemonade`, `acid` |
| 落ち着き・上品・大人 | `corporate`, `winter`, `nord`, `lofi` |
| 自然・癒し・植物 | `garden`, `emerald`, `forest`, `aqua` |
| 夜・かっこいい・ネオン | `synthwave`, `night`, `dracula`, `business` |
| レトロ・あたたかい | `retro`, `autumn`, `coffee`, `cmyk` |

DaisyUI のテーマだけで足りないときは、`public/css/style.css` で CSS 変数（`--p` 主色 など）や一部の色を上書きしてよい。ただし**やりすぎない**（後述の「抑制」）。レトロゲーム / Win98 風など DaisyUI 自体が合わないテーマは、`coding-rules.md` / `tech-stack.md` の「CSS フレームワーク差し替え」に従う。

### 2. 差し色（アクセント）

ブランド色を 1 つだけ決める。あとはニュートラル（白〜グレー〜黒）と、意味色（成功＝緑、警告＝赤）に絞る。**多色づかいは AI slop の典型**。差し色は「ボタン・リンク・強調・signature」など“ここぞ”だけに使う。

### 3. タイポグラフィ

`layout.erb` で Noto Sans JP / Inter が読み込み済み。役割を決めて使い分ける。

- **見出し（display）**：大きく・太く・字間を意図的に。ここで個性を出す。
- **本文（body）**：読みやすさ優先。サイズと行間を一定のリズムで。
- **補足・データ（utility）**：小さめ・控えめ。

サイズは段階（type scale）を決めて、その中から選ぶ（例：本文 `text-base`、小見出し `text-xl`、見出し `text-3xl`〜`text-5xl`）。サイズをバラバラに使わない。

### 4. signature（記憶に残る 1 要素）

そのサービスを「これ！」と思い出させる、**たった 1 つ**の見せ場を決める。トップの大きな見出し、特徴的なカードの形、ヒーロー画像、ちょっとした動き、など。題材を体現するものにする。**大胆さはここ 1 か所に集中**させ、周りは静かに保つ。

## 進め方：プラン → 自己批判 → 実装

1. **プラン**：上の 4 トークン（テーマ / 差し色 / タイポ / signature）と、画面ごとのざっくりレイアウトを言葉で書き出す。
2. **自己批判**：「これ、どんなサービスでも同じものを出してないか？」と一度疑う。題材を別のものに差し替えても成立してしまうなら、それは汎用デフォルト。題材ならではの選択に直す。何を変えたかを一言メモする。
3. **実装**：固まった方向性の通りに ERB を書く。色もタイポも、すべて固定したトークンから導く。実装中に思いつきで方向性を増やさない。

この計画と批判は基本クロードの頭の中（thinking）でやってよい。メンバーには、自信を持って出せる案だけ見せる。

## 抑制と自己チェック（仕上げ）

- **盛りすぎたら 1 つ外す**。装飾・色・アニメを足したくなったら、本当に題材の役に立つか問う。役立たないものは削る。「鏡を見て 1 つ外す」発想。
- **アニメは入れすぎない**。過剰な動きは逆に「AI が作った感」を強める。signature 周りに 1 つ効かせる程度に。
- **最低ラインは黙って満たす**：スマホ幅で崩れない、ボタン / 入力欄がキーボード操作でも分かる（フォーカスが見える）。レスポンシブは必須ではない（できたら褒める）が、極端に崩れないようにはする。
- **空状態を放置しない**（下記）。データ 0 件の画面は初学者の作品が一番ダサくなるポイント。

## 文言（コピー）もデザインの一部

見た目だけ整えても、文言が雑だと安っぽくなる。次を守る。

- **空っぽの画面は「次にどうするか」を示す**。「データがありません」で終わらせず、「最初の 1 件を投稿してみよう」のように行動を促す。
- **ボタンは何が起きるかを書く**。「送信」より「投稿する」「保存する」。同じ操作は最初から最後まで同じ言葉で（「投稿する」を押したら「投稿しました」）。
- **使う人の言葉で書く**。システム都合の用語（レコード、テーブル）を画面に出さない。
- **能動態・短く・素直に**。凝った言い回しより、具体的で分かりやすい言葉。

## 中高生キャンプ向けの調整（重要）

元の公式スキルは「プロのスタジオとして大胆な美的リスクを取れ」という強めのトーンだが、ここでは次に寄せる。

- **方向性はクロードが決め切って提案する**が、起点は必ずメンバーの好み・テーマ。押し付けず「君のサービスにこれが似合うと思って」と理由を添える。
- **リスクは取りすぎない**。dev-agent が全画面で再現できる範囲の“ちょっと尖った”くらいに留める。奇抜すぎると崩れる。
- **メンバーにフレームワークの話をしない**。「DaisyUI のテーマを cupcake に〜」みたいな技術判断はクロードが裏で行い、メンバーには「やさしい雰囲気にしたよ」と結果だけ伝える。

## どこに固定するか（出力先）

Design フェーズで決めた内容は、`plan.md` の末尾に次の形で書く（`spec-workflow.md` のデザイン仕様テンプレに従う）。dev-agent はここを読む。

```markdown
## デザイン仕様（固定）
- テーマ（data-theme）: cupcake
- 差し色: ローズピンク（#F472B6 系）/ それ以外はニュートラル
- 見出しフォント: Noto Sans JP / 太め・大きめ
- 本文フォント: Noto Sans JP / text-base・行間ゆったり
- signature: トップの大きな見出し＋手書き風の下線アクセント
- 雰囲気の一言: やさしくて、ノートに書くみたいな温かい感じ
```

`layout.erb` の `data-theme` は、この「テーマ」に合わせて書き換える（初期値 `light` のままにしない）。

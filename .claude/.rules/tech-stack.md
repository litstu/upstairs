# 💻 技術的な制約

## 使用技術（バックエンド）

- **言語:** Ruby 3.4.1
- **フレームワーク:** Sinatra + ActiveRecord 7.0
- **データベース:** PostgreSQL
- **サーバー:** Puma 6.4 / WEBrick 1.7
- **画像保存:** Cloudinary（必要な場合のみ）
- **テンプレート:** ERB

ライブラリのバージョンは [Gemfile](../Gemfile) で固定済み。バージョンを上げたりしないこと。

### サーバー起動の設定（Cloud9 用）

このキャンプの開発環境は **Cloud9** が基本。`app.rb` には下記の設定が **必ず必要**：

```ruby
set :bind, '0.0.0.0'
set :port, 8080
```

理由：Cloud9 は `localhost:4567` のような独自ポートをブラウザから直接見られない。プレビュー機能が許可するのは **`8080` / `8081` / `8082`** のみ、かつ `0.0.0.0` バインド必須。

メンバーが見るときの方法（Cloud9）：上部メニュー **Preview → Preview Running Application**（`localhost:8080` を直接打っても見えない）。**IDE 内蔵のプレビューは CDN（Tailwind / DaisyUI / フォント）がうまく読み込めずデザインが崩れることがあるので、プレビュー右上のポップアウトボタンで必ず別タブで開くよう案内する**。

## AI に問い合わせる機能（AI Gateway）

メンバーのサービスが **AI に問い合わせる**（チャット、自動生成、相談、診断、要約など）場合は、**AI Gateway を使う**。OpenAI / Gemini などの外部 AI API を直接叩かない。これが唯一の AI 利用ルート。

> **AI にネット検索させられる（`ask_ai` に組み込み済み）。** `ask_ai` には `web_search` ツールが最初から入っていて、AI が必要と判断したら **ゲートウェイが検索して最新情報をふまえた答えを返す**（`toolChoice: auto`。今日のニュース・現在の価格なども可能）。受け取り方はいつもと同じ（テキストが返る）ので、呼び出し側に追加のコードは要らない（`ask_ai` に組み込み済みなので）。拾えるのは**公開 Web の範囲・鮮度に依存**する（何でも必ず最新、ではない）。※ さらに**自作の関数を AI に呼ばせたい（Function Calling）**場合は、`tool_use` が返ったらアプリ側で実行して結果を返す 2 往復の実装を足す（`web_search` 以外のツール名はゲートウェイが横取りせずアプリに返す）。※ センサーで測る“今の現実の状態”（混雑・在庫など）は web_search でも取れないので `spec-workflow.md` の危険ファミリー A の通り立て直す。

### 最初から用意されている道具

- **`app.rb` に `ask_ai(messages)` 関数が最初から入っている**（黒box として使う。中身を書かせない）。`messages` を渡すと AI Gateway に送って回答テキストを返す
- **`faraday` gem は Gemfile に入っている**（通信用）。`dotenv` で `.env` を読み込み済み
- **接続先・アクセスキー・モデルは、セットアップスクリプト（`member-scripts/lit-webs-ai.sh`）が設定した環境変数を `ask_ai` がそのまま使う。** `.env` にキーを書く必要はない（鍵をプロジェクトに残さない＝ GitHub 流出防止）
  - `ANTHROPIC_BASE_URL`＝接続先 / `ANTHROPIC_AUTH_TOKEN`＝アクセスキー / `AI_GATEWAY_MODEL`＝サービス用モデル
- **サービスのモデルは Haiku**（`AI_GATEWAY_MODEL` にセットアップが設定）。Claude Code 本体は Sonnet（`ANTHROPIC_MODEL`）だが、サービス側はコストの軽い Haiku を使う。ハードコードせずスクリプトの値を読むので、メンターが配布値を変えれば追従する

### dev-agent が AI 機能を実装するとき

`ask_ai` を呼ぶルートを書くだけでよい。`messages` は **Converse 形式** で組み立てる：

```ruby
get '/result' do
  # ユーザーの入力を AI に渡す
  messages = [
    { role: 'user', content: [{ text: params[:response] }] }
  ]
  # 返答は markdown のまま受け取る（表示側で整形する）
  @result = ask_ai(messages)
  erb :result
end
```

ビュー側は `data-markdown` に入れるだけで整形表示される：

```erb
<div data-markdown><%= @result %></div>
```

- 事前プロンプト（キャラ設定・指示文）を足したいときは、`messages` の先頭に `{ role: 'user', content: [{ text: '...' }] }` を加える
- **`ask_ai` 関数自体は書き換えない・再生成しない**（最初からある道具）
- `.env` にキーを書かせない（鍵を残さない）。接続はセットアップ済みの環境変数で自動的に通る
- **AI の返答は markdown で返ってくる前提で表示する**（`**強調**` / `# 見出し` / `- 箇条書き` / ` ```コード``` ` など）。プレーン化しようとせず、**markdown を整形して見せる**。
  - **やり方：AI の返答を `data-markdown` を付けた要素に入れるだけ。** `views/layout.erb` に読み込み済みの `marked.js` が、読み込み時に自動で HTML へ変換し、`prose` クラスで見た目も整える。
    ```erb
    <%# 例：AI の返答を markdown として整形表示 %>
    <div data-markdown><%= @result %></div>
    ```
  - この方式なら **`gsub("\n", "<br>")` は不要**（marked が改行・見出し・リスト・コードを整形する）。
  - JSON を返させる用途（クイズ生成など）は別。AI が ` ```json ... ``` ` で囲って返すことがあるので、パース前に ` ``` ` を取り除いてから `JSON.parse` する（表示ではなくデータとして使うため data-markdown は使わない）。

### メンバーへの伝え方

AI の接続はセットアップ（`lit-webs-ai.sh`）で自動的に整うので、メンバーが `.env` にキーを入れる必要はない。実装した AI 機能が動かない場合は、まず **セットアップが済んでいるか**（ターミナルで AI が使える状態か）を確認する。環境変数が無い状態なら「もう一度セットアップ（`source ...lit-webs-ai.sh`）をやってみよう／メンターさんに聞いてみて」と促す。アクセスキーの値そのものはチャットに貼らせない。

## フロントエンド（CDN ベース、ビルド不要）

JavaScript フレームワーク（React / Vue など）は使わない。HTML / CSS / 素の JavaScript で構築。**デザイン系のライブラリは CDN 経由で読み込む**。`views/layout.erb` にデフォルトで下記が仕込んである：

| ライブラリ | 用途 |
|---|---|
| **Tailwind CSS（CDN 版）** | レイアウト・色・余白などのユーティリティクラス。`class="flex p-4 bg-pink-100"` のように書く |
| **DaisyUI** | Tailwind 用のモダンな UI コンポーネント。`class="btn btn-primary"`, `class="card"` などで shadcn / Linear 風の見た目に |
| **Google Fonts** | `Noto Sans JP`（日本語）/ `Inter`（英数字）を読み込み済み |
| **Phosphor Icons** | 線画系の SVG アイコン。`<i class="ph ph-heart"></i>` のように使う |

### デザイン系ライブラリを差し替えてよい場合（クロードが判断する）

メンバーから「もっと○○なデザインがいい！」と要望があった or サービスのテーマに対して **デフォルトの Tailwind+DaisyUI が合わないとクロードが判断した** 場合、**メンバーに相談せずクロードが勝手に判断して別の CDN ライブラリに切り替える**。CSS フレームワーク選びの話をメンバーにしても理解の助けにならないので、技術判断はクロードが主導する。

切り替え時の考え方：

| サービスのテーマ | 候補 |
|---|---|
| レトロゲーム / ピクセルアート系 | **NES.css**（ファミコン風） |
| Windows 95 / 98 風のジョーク系 | **98.css** / **XP.css** |
| 雑誌・読み物系・上品な明朝体 | **Almond.css** |
| シンプル・ミニマル・ピンク系 | **Sakura.css** |
| 新聞風・クラシックな品 | **Pico.css** |

切り替えるときは：
1. `views/layout.erb` の Tailwind/DaisyUI の `<script>` / `<link>` を **コメントアウトする**（消さない、戻せるように）
2. 新しい CDN を追加
3. メンバーには「君のサービスにこういう雰囲気が似合うと思って、デザインのベース変えたよ〜！」程度に **結果報告だけ** する（事前相談はしない）

### Cloudinary 以外の有料外部サービスは使わない

CDN は無料の jsdelivr / unpkg / fonts.googleapis.com などからのみ読み込む。

### ファイル/フォルダ追加のルール

**基本はこの構成のままで作る。** ただし `app.rb` が肥大化してメンバーが読みづらくなるレベル（**目安：300 行を超える**）なら、**例外的にディレクトリを増やしてよい**。たとえば：

- ルートが多い → `routes/posts.rb`, `routes/comments.rb` のように分割
- 共通ロジック（投稿件数を数える、タグを整形するなど）が複数箇所で使われる → `helpers/` に切り出し

**ただしテストファイル、エラーハンドリング専用ファイルは作らない。** あくまで「コードを読みやすくするため」の分割だけ許可。

判断基準：
- ✅ メンバーが「どこに書いてあるかわからない」と感じるレベルなら分割 OK
- ❌ 「綺麗に書きたいから」「プロっぽく見せたいから」だけの理由では分割しない

## 画像保存：基本はローカル保存（`public/uploads/`）

画像アップロード機能が必要な場合、**外部サービスは使わず、サーバー上の `public/uploads/` フォルダに保存** する。Sinatra なら `params[:image][:tempfile]` を `File.open` で書き出すだけ。

### Sinatra でのローカル保存の基本形

```ruby
# 投稿フォームでアップロードされた画像を保存する
post '/posts' do
  image_path = nil
  if params[:image] && params[:image][:tempfile]
    # ファイル名は重複しないようにタイムスタンプを頭に付ける
    filename = "#{Time.now.to_i}_#{params[:image][:filename]}"
    # public/uploads/ に書き出す
    File.open("public/uploads/#{filename}", 'wb') do |f|
      f.write(params[:image][:tempfile].read)
    end
    # データベースに保存するパスは "/uploads/..." 形式
    image_path = "/uploads/#{filename}"
  end
  Post.create(image_path: image_path, body: params[:body])
  redirect '/'
end
```

`public/uploads/` フォルダは事前に作っておくこと（実装時に dev-agent が作る）。`<img src="<%= post.image_path %>">` で表示できる。

### `.gitignore` にユーザーアップロード分を追加

`public/uploads/*` は中高生のテスト投稿が入るので git にコミットしない方針。`.gitignore` に下記を入れる：

```
public/uploads/*
!public/uploads/.gitkeep
```

`.gitkeep` を空ファイルで置いておくと、フォルダ自体は git で管理される。

### Cloudinary を使う場合（応用）

メンバーが本格的にネット公開したい / メンターが「Cloudinary 使う？」と提案した場合のみ、Cloudinary に切り替える。

- 環境変数: `CLOUD_NAME`, `CLOUDINARY_API_KEY`, `CLOUDINARY_API_SECRET`
- `.env` ファイルで管理（`.env` は gitignore 済み ── コミットしない）

#### 大原則：必ずメンターと一緒に進める

Cloudinary のセットアップは **メンバーひとりにやらせない**。アカウント・API キー・`.env` 編集は全部 **メンターとペア** で進める。

- ❌ メンバーに自分でアカウント作らせる
- ❌ メンバーに API キーをチャットへ貼らせる
- ❌ メンバーが ひとりで `.env` を編集する
- ✅ メンターが画面を見ながら、メンバーと一緒に設定する

#### クロードの振る舞い

メンター同伴を確認できたら、ステップごとにやさしく案内する：

```
メンターさんから下の 3 つの値を見せてもらってね：

- Cloud Name（短い文字列）

##### ステップ 2：`.env` ファイルを作る

```
プロジェクトのいちばん上のフォルダに `.env` っていうファイルを作るよ。

中身はこんな感じ：

##### 動かないとき

```

2. `=` の前後にスペース入ってない？
3. 値の前後にクオート `"` `'` 入ってない？
4. ファイル名が `.env`（ドット始まり）になってる？
5. サーバー再起動した？（`.env` は再起動しないと反映されないんだ）

メンターさんに API キーの値が正しいかもう一回見てもらってね！

#### 共通ルール

- ✅ **メンター同伴のときだけ** 手順を進める
- ❌ メンバー単独で「やってみる」と言われたら **必ず止める**
- ❌ API キーの値そのものをチャットに貼らせない（メンターが手元で打ち込む）
- ✅ 困ったら全部メンターに聞いて OK と何度でも伝える

## 外部 API のルール

### 2段階の判断基準

| レベル | 条件 | 対応 |
|--------|------|------|
| ✅ **そのまま使う** | キー不要 + 無料 + 認証なし | クロードが勝手に使う |
| ✅ **メンターと使う** | キー必要だけど **無料枠あり**（クレカ不要 or メンターが管理） | メンターが API キーを渡す。`.env` に入れる |
| ❌ **使わない** | 有料 or クレカ登録必須 or レート制限が厳しい | 代替案を提案 |

### レベル1: そのまま使う（キー不要 + 無料 + 認証なし）

下記の **3 条件をすべて満たす** API は、クロードがその場で試して、動けば採用 OK：

1. **API キーが不要**（登録・サインアップ不要）
2. **完全無料**（フリープランの制限内ですらない）
3. **公開エンドポイント**（HTTP リクエスト 1 発で叩ける）

例：
- ✅ 公開 RSS フィード
- ✅ オープンデータ系の JSON エンドポイント（気象庁の天気予報、政府統計データなど）
- ✅ Wikipedia API（キー不要）

### レベル2: メンターと使う（キー必要 + 無料枠あり）

下記のような API は、**メンターが API キーを管理する形** で使ってよい：

- **Google Maps JavaScript API / Embed API**（無料枠で十分）
- **Google Maps Geocoding API**
- **Cloudinary**（画像ホスティング。既にルールあり）
- **キャンプ側で事前にキー発行しておいた API**

運用：
- `.env` に `GOOGLE_MAPS_API_KEY=xxx` のように環境変数で管理
- メンバーに API キーの値を直接見せない・チャットに貼らせない
- セットアップは **必ずメンターと一緒に** 行う（Cloudinary と同じ運用）

#### メンバーから「○○ API 使いたい」と言われたとき

まずクロードが下記を確認する：
1. その API に無料枠はあるか？（WebSearch で調べる）
2. クレカ登録なしで使えるか？
3. キャンプ期間中に制限に引っかからない程度のレート制限か？

3つとも OK → 「メンターさんに相談して、一緒に設定しよう！」と案内
1つでも NG → 代替案を提案

声かけ例（OK の場合）：

```
お、○○ API 使いたいんだね！調べてみたら無料で使えるっぽい！

ただ API キーっていう「合言葉」が必要だから、
**メンターさんと一緒に設定しよう**！

メンターさんに「○○ API 使いたいです」って伝えてみて〜
一緒に来てくれたら僕もセットアップ手伝うよ！
```

### レベル3: 使わない（有料 / クレカ必須 / 制限厳しい）

- ❌ Twitter/X API（有料プランのみ）
- ❌ OpenAI / Gemini API（有料。ただし AI Gateway 経由は別ルール）
- ❌ YouTube Data API v3（クオータが厳しすぎる）
- ❌ Spotify API（OAuth 必須 + 開発者登録が煩雑）

代替案の提案例：

```

設定がめちゃくちゃ大変だから、今回のキャンプでは使えないんだ💦

代わりに、こういう形にしたらどうかな？
- [代替案1]
- [代替案2]
```

### 試して動かなかったときの対応

クロードが「動かないかも」と思ったら、**メンバーには結果だけ伝える**：

```
さっき試してみたんだけど、その API ちょっとうまく動かなかった〜！💦
ごめんね、別の方法で似たようなことできないか考えよう！
たとえば...（代替案を提案）
```

決して「API キーを取得すれば動きます」とか言わない。**キャンプ期間中にメンバーが現実的に使えるかどうか** で判断する。

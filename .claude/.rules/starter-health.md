# スターターの健全性（最初から動く状態を守る）

このスターターは **完璧ではない**。でも「配布した時点で動く」状態にはなっている。クロード（dev-agent 含む）は、その **最初から動く状態を壊さない** ことを最優先で守る。凝った作り替えや“きれいにしたい”だけの改造で、起動しなくなるのが一番まずい。

## 大原則

- **スターターの初期構成・設定を過剰に作り替えない。** 迷ったら「動く状態を保つ」を選ぶ。
- **配布時点の「`bundle install` → `ruby app.rb` で起動する」を必ず維持する。** これを壊す変更はしない。
- `app.rb` / `Gemfile` / `models.rb` / `config/` / `db/` を触ったら、**必ず起動確認してから完了**とする（後述の順番）。
- 完璧じゃなくていい。**動いて、メンバーが「自分のサービスが動いた！」と体験できること** が最優先。

## 完了の前に必ずやる起動確認（順番）

`/speckit-build` の完了前や、`app.rb` などを変更したあとは、この順で確認する（詳細は `speckit-build` フェーズ 2.5 と `coding-rules.md` のスモークテスト参照）：

1. `~/.rbenv/shims/bundle install` ── gem を入れる（**未インストールが一番多い原因**）
2. `~/.rbenv/shims/bundle exec rake db:create db:migrate db:seed` ── DB を用意
3. スモークテスト（サーバー起動 + GET ルート網羅 + AI を使うなら実通信）
4. すべて通ってから「完了」とメンバーに伝える

## エラーが出たときの切り分け（完成品・実装後 共通）

サーバーが起動しない / 500 が出る / AI が動かない、といったときは **この順で切り分ける**。メンバーには技術詳細を見せず、クロードが裏で対処する。

1. **gem 未インストール**（`cannot load such file` / `LoadError`）→ `~/.rbenv/shims/bundle install`
2. **bundler バージョン不一致**（`/usr/bin/bundle` の古い Ruby を踏んでいる）→ 必ず `~/.rbenv/shims/bundle` を使う
3. **DB 未準備 / マイグレーション未適用**（`PG::` 系, `relation does not exist`）→ `rake db:create db:migrate db:seed`
4. **`.env` 未設定**（AI を使うのに `AI_GATEWAY_URL/KEY/MODEL` が空）→ メンターにキーをもらって `.env` に入れてもらう
5. **コード起因**（テンプレート構文ミス、`@変数` と erb の不一致など）→ ログ / スタックトレースを読んで該当を修正（dev-agent に依頼）
6. **どうしても直らない** → 深追いせずメンターを呼ぶ導線に切り替える（「メンターさんと一緒に直したい」と正直に）

## やらないこと

- 動いている初期構成を「プロっぽくしたい」だけの理由で作り替える
- 起動確認をせずに「完了」と言う
- エラーを握りつぶして“動くフリ”のまま完了扱いにする（`spec-workflow.md` の「そのアイデア、本当に作れる？」と同じ精神）
